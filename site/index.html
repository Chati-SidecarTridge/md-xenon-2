50 frames a second on a 1989 Atari ST

In 1989 The Bitmap Brothers' Xenon 2 Megablast showed a new picture every third vertical blank: 16.7 frames a second. This is the whole game rewritten in C for the small computer in a SidecarTridge Multi-device, so that the same ST, unmodified, shows a new picture at every one of its 50.

This page explains how it was built. Choose how deep to read at the top: Advanced user adds how each machine behaves, the card's files and the timings; Developer adds the code, the memory maps and the protocols.

Why 16.7

The Atari ST has no sprites and, before the STE, no hardware scrolling. Everything a game shows, the 68000 at 8 MHz draws itself, word by word, into the screen's memory: the scenery moving down, the ship, every enemy, every bullet, the explosions and the status bar. Xenon 2 does all of that and plays David Whittaker's music at the same time, and it takes at least three vertical blanks to finish a picture. A PAL ST has fifty vertical blanks a second, so the game runs at 16.7 frames a second.

It was a remarkable game at that pace. The question this project asks is what it would have looked like on an ST that had a graphics chip.

Advanced user

The original draws into one screen while the ST shows the other, and swaps them when the picture is finished, never sooner than three vertical blanks after the last swap. Its music runs from the vertical blank interrupt, fifty times a second, whatever the frame rate. So in the original the scroll, the ship and the enemies all move once per picture, and the music keeps its own time.

Developer

The game's rules move in steps of one original frame. scroll.c holds the original's scroll rule as it is: the world line, the set speed, the doubling after 35 frames off it, the lowest line, the 16-line reverse window, the backdrop's half step on odd frames. scroll_pace() turns vertical blanks into steps with a phase in 1/256ths of a VBL, so a step can be any number of VBLs, not only three.

A graphics chip in the cartridge slot

The SidecarTridge Multi-device sits in the ST's cartridge slot. Inside it is a Raspberry Pi RP2040: two Arm Cortex-M0+ cores, here at 225 MHz, 264 KB of RAM and 2 MB of flash. To the ST it looks like a cartridge ROM: 128 KB of memory the ST can read at any moment, which the RP2040 serves with its programmable I/O and DMA, without the CPU's help.

This port treats the cartridge as the graphics chip the ST never had. The RP2040 runs the whole game and draws every picture. The ST only shows them, plays the sound and reads the joystick. Each picture goes through four steps, every vertical blank:

  1. RP2040

    Draw

    The game draws a 320 × 200 picture into the RP2040's RAM, one byte per pixel: easy and fast to draw into.

  2. RP2040, both cores

    Convert

    The ST's screen stores each pixel's colour as four bits spread across four planes. Both cores convert half the picture each, in hand-written assembly, in about 1 ms.

  3. Cartridge window

    Publish

    The 32,000 bytes go into the cartridge's memory, laid out for the ST's copy, and a frame counter moves on.

  4. Atari ST

    Copy and show

    At the vertical blank the ST copies the new picture to the screen page it is not showing, then shows it. A page is never shown half written.

The ST's copy is the expensive part. A fully unrolled loop of movem.l instructions moves 48 bytes per pass, 666 passes for the whole screen: 17.65 ms on a Mega ST, measured, exactly what the 68000's timing tables predict. The cartridge adds no wait states. On an STE or a Mega STE, the blitter does the copy instead.

Advanced user

The cartridge's 128 KB are two windows: $FA0000, the cartridge proper, which holds the ST's program and everything the two sides share, and $FB0000, which the ST only reads to send signals (see the read-only port). The ST's program is 16 KB at most. It starts from the cartridge before the desktop and the AUTO folder, copies a little of itself into RAM, and takes over the vertical blank, the keyboard and the sound chip. It needs a colour monitor: in high resolution it returns to the desktop with a message.

The two screen pages sit at $70000 and $78000, within the first 512 KB. Any ST, STE, Mega ST or Mega STE runs the same program; it asks TOS whether there is a blitter and checks the machine's type for the DMA sound chip.

Developer

Chunky to planar. Four pixels sit in one 32-bit word, a byte each with the colour in its low nibble. One multiply gathers the four bits of a plane into a nibble:

/* q: four pixels, one byte each. Plane k's four bits, in order. */
uint32_t nibble = (((q >> k) & 0x01010101u) * 0x80402010u) >> 28;

The worker, fb_c2p_half in fb_chunked_asm.S, runs that over a range of the picture with the two constants in registers and no lookup table. Core 0 converts the top 100 rows while core 1 converts the bottom 100, handed the job through the inter-core FIFO (fb_core1_dispatch / fb_core1_wait, the only way the app uses core 1).

The copy, backwards. The ST's loop is pairs of:

movem.l (a6)+,d0-d7/a1-a4    ; 48 bytes from the cartridge
movem.l d0-d7/a1-a4,-(a5)    ; to the screen page, walking down

The pre-decrement store is 4 cycles a pass faster than an indexed one, but it lays each chunk at a lower address than the one before. So the RP2040 publishes the picture with its 48-byte chunks in reverse order (fb_chunk_reverse_copy48), and each lands where it belongs. a0 and a7 stay out of the register list: a0 is the sound interrupt's cursor and a7 keeps the stack valid so interrupts can fire in the middle of the copy. FB_COPY_LINES sets how many lines are copied.

No tearing. The RP2040 bumps a frame counter as the last write of each publish. The ST copies only when the counter's low word has changed since its last copy (one move.w: a longword arrives as two reads with its halves swapped), then flips and acknowledges by reading $FB84xx. The RP2040 waits for that acknowledgement before it writes the next picture. A game slower than a frame drops frames instead of tearing them.

Twenty milliseconds

Everything the ST does has to fit between two vertical blanks: 20 ms. The project measures it with a stopwatch built from one of the ST's own timers, which marks the points of each frame on a single timeline that the RP2040 reads.

On a Mega ST that leaves about a quarter of a millisecond. Anything more the ST does comes out of it: every byte from the keyboard is an interrupt of 30 to 40 µs. That is why the ST does nothing of the game at all. Its whole program, the copy, the sound, the keyboard, fits in 16 KB of cartridge code, and of the ST's RAM it uses only its two screen pages and, on an STE, the sound chip's buffer.

Advanced user

When a copy ends after the next vertical blank, that picture waits one more: the frame rate drops, the sound does not break. The joysticks send a byte only when they move, so play stays at 50. The blitter copies in pieces of 40 chunks, about 1 ms each, so the keyboard's interrupts still run between them. On a Mega ST fitted with a blitter, whose samples go through the YM, letting the blitter hold the bus delays the sound's interrupts and roughens it, so there the 68000 copies.

Developer

The stopwatch is TIME_STUDY = 1 in userfw.s (off in releases; it costs about 40 µs a VBL). MFP Timer-A runs free at /10, 4.07 µs a tick; an interrupt counts its wraps. The VBL and four points of the loop (the wake, the copy's start and end, the loop's end) each report the ticks' low 16 bits by reading $FB8Bxx (the point) and $FB8Cxx / $FB8Fxx (the ticks), so every duration is a difference on one timeline, even across a VBL. With a Debug Probe, tools/dev/swd.py stopwatch reads the points and the slack histogram (fbSlackHist) from the running RP2040.

The sample interrupt is measured at about 152 cycles, not the 112 of the tables: the MFP's acknowledge and the sound chip's accesses add the rest. Who copies is a word the RP2040 sets (CART_BLIT_MODE_OFFSET): auto (the blitter only with DMA sound), the blitter, or the 68000, with the chunks per piece in its high byte.

A read-only port that talks back

A cartridge port only lets the ST read. It has no way to write to the cartridge, so the ST talks to the RP2040 by reading: it reads an address in a second 64 KB window, and the address is the message. The high byte says what it is, the low byte carries a value.

  • a key or a joystick byte read at $FB82xx, one per byte from the keyboard processor
  • the sound's position read every vertical blank, so the RP2040 writes the next samples just ahead of what plays
  • the picture shown read after each copy, so the RP2040 never overwrites a picture the ST is still copying
  • hello read at every boot, with the machine and the TOS version

The RP2040 records every read of that window in a ring buffer with DMA, with no interrupt per read, and its main loop decodes them. The keyboard processor's packets, the mouse and both joysticks are all decoded on the RP2040, with rules for every way a byte can be lost so that a lost byte never becomes a key press.

Advanced user

The other direction is easy: the RP2040 writes into the cartridge's memory and the ST reads it. That is how the ST learns to leave. Esc on the title writes a command word that the ST's loop reads every frame; it puts back what it took from TOS (the interrupts, the keyboard processor's modes, the sound chip) and returns to the desktop.

X on the title returns to the Multi-device's menu, Booster, without switching off: the RP2040 saves Booster as the next app and restarts itself, while the ST, told to reset, copies a small routine into the unused end of a screen page (the cartridge stops answering while the RP2040 restarts), waits a couple of seconds, and resets cold. The ST's reset button works at any time; the RP2040 keeps running and answers the next boot's hello.

The keyboard processor is set to report both joysticks as events with the mouse off. Port 1 is the player's joystick, and the keyboard works throughout.

commemul.c runs a PIO program and a DMA chain that store every address read in the window into a 4 KB ring; the main loop drains it with commemul_poll(), and a reader that falls a whole ring behind is counted and resynchronised. The ST reads the keyboard ACIA from its receive interrupt, one byte an interrupt, and forwards it with a read; polling it from inside the copy left gaps longer than a byte time and lost bytes.

The decoder (ikbd_demux.c, plain C, host-tested) watches for every sign of a lost byte: an overrun, a full ring, the ST's byte count not matching what arrived, a packet open at its second VBL, an invalid joystick byte, a packet never asked for. After one it holds back presses, mouse and joystick data until a VBL in which the ST read no byte, where the stream is certainly back in step; releases always pass, so no key stays down. The RP2040 owns the keyboard processor's commands too: a block of generation, length and up to 12 bytes that the ST sends a byte per VBL, only when the ACIA can take one.

The command word at $FA4000 is a level, not a queue: the ST samples it once a frame, the RP2040 clears it only on a hello. The RP2040 can also refuse a boot by setting a status word and a message that the ST prints before returning to the desktop.

Taking the game apart

Nothing of the game is in this project. The firmware doesn't contain a single picture, sound or table from it. The player puts their own copy of the two original disks on the cartridge's microSD card, as Pasti .stx images of the Image Works release, and the cartridge converts it.

To do that, the cartridge reads the disks the way the original's loader does: the boot program's two layers of decryption, the game image's chained XOR passes, the levels' own sector stream, and the LHarc compression of each level. The game's code was studied in the Hatari emulator, with scripts that run the original headless, press its keys, and record its memory, its disk accesses and its screens. Those tools are in the repository too. What they produce never is.

At every start the cartridge checks the manifest: the converter's version and every file's size. A file missing or of another size makes the set again, in a few seconds; a level image whose header doesn't match is made again, in 6 to 9 seconds. Delete SET to start over. The disks are recognised by their files' CRC-32s: the Kixx re-release and other dumps convert to something else and are refused with a message and a QR code to the instructions.

Developer

The converter is plain C with no SDK: x2game.c (the loader's decryption, the level stream's virtual sectors, the CRC-32s of the known release in x2_known), stx.c (Pasti images, sector by sector on demand), lzhuf.c (LHarc -lh1-, about 8.6 KB of state, the caller's) and crc32.c, streaming through the hooks in x2io.h. The same sources build tools/x2conv on a computer, which makes the same bytes and the images the store holds. Host tests run the C core under AddressSanitizer and UBSan against the Python reference (tools/re/x2disk.py) on synthetic disks; no test uses a byte of the game. The set's format is in docs/set-format.md.

The study tools are in tools/re. hatari_run.py runs the original in Hatari headless, one folder a run, driven by expectation files that wait on Hatari's output (an FDC trace line, a breakpoint), press keys and fire, swap disks and run debugger command files; fdc_map.py turns an FDC trace into a load map; render_level.py draws a playfield exactly as the original does, the reference the RP2040's renderer is checked against.

Routine by routine

There is no 68000 emulator in the cartridge. Every part of the original was read, understood and written again in C: the scroll, the ship and its weapons, the paths and the fire of every enemy, each level's own code and bosses, the shop, the attract screens, the sound driver. The C reads only the game's data from the converted disks: its levels, pictures, songs and tables, at the addresses the original keeps them.

Each routine was checked against the original running in Hatari:

  • The enemies' positions on level 1 match the original's frame for frame.
  • The scenery is drawn pixel for pixel as the original draws it.
  • Every one of the sound chip writes in 87,032 calls of the music driver is the original's.
  • The screens outside play, the shop included, keep the original's pace through a model of the ST's clock: each drawing step costs the 68000 cycles the original's takes.

The whole game is about 347 KB of code for the RP2040. Drawing the playfield of 192 lines from the level's map takes about 1.5 ms of one core.

Advanced user

What differs from the original, on purpose: the high-score table is kept on the cartridge (the original keeps it only until the ST is switched off); the options screen; Esc and X on the title; and the frame rate. Everything else, the waves, the bosses' patterns, the shop's prices and offers, Crispin's advice, the two players' turns, is the original's rule.

Developer

The objects. enemies.c is the original's object system: a pool of 96 objects on the heap, the wave and scenery tables fired by the world line, the spawner (trails, rows, chains, groups), the path interpreter, fire, hits, explosions, cash, capsules, tokens and restart points. A dead object is freed when the update walk reaches it, as the original frees it, so the objects behind it still see it that frame. Each level's own code sits behind a table of hooks (enemies_level.h: its scenery kinds, its every-frame code, its objects' updates, hits and drawing), one file a level, level1.c to level5.c.

The screens. The original's screens wait for frames in the middle of their routines. screen.c turns each into a coroutine (pt_t) stepped a VBL at a time, on a model of the ST's clock: each drawing step costs what the original's takes in 68000 cycles (fitted to Hatari's timings), a frame is at least 3 VBLs, and the swap comes at the picture's end. That is how the shop and the attract keep the original's pace at any frame rate.

The rule. No 68000 interpreter, anywhere on the RP2040. An interpreter of the original's code may serve on a computer as a reference while porting, never in the firmware: the firmware reads only the game's data, and every routine is C that can be read, tested and timed.

Tests. make -C tests/host test builds firmware units unchanged with the host compiler under the address and undefined-behaviour sanitizers, with core 1 as a thread: the scroll, the ship, the weapons, the enemies, the world's renderer against a planar reference, the sound driver, the shop, the screens, the options, the blits' clipping, the chunk layout through a model of the ST's copy, the keyboard decoder under lost bytes, the audio against a simulated ST and STE. They run on synthetic data, in a few seconds, on every pull request.

Three times the frames

Running the original's rules three times as often would make it a different game: three times as fast. So the frame rate and the game's speed are separate choices.

At 50 frames a second the world always scrolls a line every vertical blank. The ship, the shots and the enemies can then keep the original's speed: the game's logic still steps every third vertical blank, and every picture in between draws each object between where it was and where it is. What rides on the scenery, a wall gun or a boss, moves with the line drawn. Or they can all run three times as fast, an option the players call ×3.

At 17 frames a second, with the options at their originals, it is the 1989 game, untouched. The options screen chooses the rest: the damage a hit takes, the lives, the shots ×3, the level to start at.

Shots ×3 steps only your weapons three times per step of the game, held fire's timer included, so your shots travel and repeat faster while the enemies keep their pace. The music is never sped up: it ticks every vertical blank, as on the original. Damage, lives and the start level are cheats in the plain sense. Every choice is kept on the cartridge, and F9 restores the defaults: 50, sprites original, a hit takes 1, 5 lives, shots ×3, level 1.

Developer

At 50 with the sprites at the original's speed, a step of the game runs every third VBL, and the VBLs between run only the world (world_vbl() in play.c): the last step's scroll again, so waves still fire as the world reaches their line. Before each step enemies_snapshot() and weapons_snapshot() keep every object's place; when drawing, each is pulled back by the part of its last move not yet shown:

/* the part of the last step not shown yet, in 256ths */
back = (vbls_per_step - shown) * 256 / vbls_per_step;
x -= (dx * back + 128) >> 8;      /* en_back() */
y -= (dy * back + 128) >> 8;

Three refinements make it look right. What rides the world is moved with it to the line drawn, and its last move is taken against the world, which moves in whole lines, so a gun on a wall stays on the wall (place() in enemies.c). Objects that keep a world line of their own (the level 1 and 2 bosses, level 3's walls, level 4's movers: enemy_t.world) are drawn from it. A move longer than 32 pixels for an enemy, 112 for a projectile, is a jump, a new object or a teleport, and is drawn where it lands.

The frame rate lives in the options as VBLs a step in 1/256ths, so scroll_pace() needs no special case, and the options are packed into one setting (OPTIONS; 0 means every original value).

Where the game lives

The RP2040 has 264 KB of RAM, and the picture alone takes 96 KB of it: 64 KB to draw into, 32 KB to convert into. A level doesn't fit beside it, so the game reads its levels in place from flash.

384 KB of flash
the firmware: the framework and the whole game's code
768 KB of flash
the store: the level being played, the screens outside play, the title tune and the graphics every level shares
The microSD card
the two disk images and, made once at the first start, each level as an image ready for the store

When a level starts, its image is copied from the card into the store's 400 KB slot, in about two seconds for the largest. A level already in the store is not written again. While the flash is written, the ST keeps running: the cartridge is served from RAM, and the second core waits in code that runs from RAM too.

The store isn't in the UF2: the cartridge fills it from your card. Its sections are made once, each checked by a header and the CRC-32 of the file it came from, and a level's slot is rewritten only when another level starts. A flash sector lasts around 100,000 erases; a slot rewritten at every level change will outlast any player. The options and both high-score tables are kept in the app's settings sector, beside Booster's.

Developer

Writing flash under a running ST. The cartridge is served by PIO and DMA from the 64 KB window in RAM, so the bus doesn't need flash. store.c erases in 64 KB blocks (about 150 ms each) and programs 4 KB sectors, each with interrupts off; core 1 is parked in a loop that runs from RAM (never write flash while a job runs on core 1). An image's magic is programmed last, so a power cut mid-copy leaves a slot that fails its check and is made again.

Pitfalls we hit.

  • Never let a DMA read the flash while the cartridge is live. An SD card write from a pointer into flash held up the DMA that answers the ST, and the ST crashed with four bombs. The level images go to the card through a 4 KB RAM buffer.
  • Core 0's stack is 4 KB, with an MPU guard below it. The converter's stack plus FatFs's did not fit, so the converter writes only to flash and a second pass copies flash to the card; large locals moved to the heap.
  • newlib grows the heap by a whole request its top block cannot hold, so a large allocation could fail with more than enough free. The heap is grown to its limit once at boot; every allocation is checked.
  • The cartridge must answer 0.4 s after power-on, when TOS looks for it. Nothing slow may run before the image is in RAM: the first start's conversion runs later, behind a screen.
  • Never read the RP2040's flash over SWD while the firmware writes it: the debugger's reads locked the chip up.

Sound

David Whittaker's music and effects come from the original's sound driver, translated to C. It runs on the RP2040 every vertical blank, as the original runs it from its own, and writes its sound chip registers into a small ring in the cartridge's memory. The ST plays them into its YM2149 at its next vertical blank.

The title tune is sampled. Its samples are converted from the disks and played through the DMA sound chip on an STE or a Mega STE; elsewhere the YM2149 plays them, two of its channels mixed to reach about six bits of resolution.

Advanced user

The music and effects always play on the YM2149, on every machine, as they did in 1989. Only the samples (the title tune and the shop's) take the DMA chip on an STE or a Mega STE, at 12,517 Hz; on a plain ST or a Mega ST they play through the YM at 5,585 Hz, a timer interrupt writing two of its volumes per sample. F8 in the options sends an STE's samples to the YM too, from its next reset.

Developer

sfx.c is the driver: the effect requests (channel 2, then 1), then the tick, every VBL, its state kept in the cartridge window at the original's addresses (CART_SFX_WINDOW_OFFSET) so the songs' and effects' bytes are read in place. Its register writes go into ym_ring, words of a register and a value with an end marker written before each new word, at CART_YM_RING_OFFSET; the ST's VBL drains them into the YM. Checked against Hatari: every write of 87,032 driver calls.

The samples go through the framework's audio path. On the YM, the cartridge holds four slices of a VBL each; the ST reports the slice it starts each VBL and the RP2040, from a 4 ms timer interrupt, writes only the slices after it, from a FIFO the main loop tops up, so the sound never tears or repeats whatever the frame rate. Each 8-bit sample maps through a 64-entry table of channel A and B volume pairs, which reaches about 6 bits from the YM's logarithmic volumes. On the DMA chip, the ST copies a 4 KB mirror into a ring in its RAM at $6F000, three VBLs ahead of where the chip plays, which it reports every VBL; byte i of the ring is byte i XOR 1 of the RP2040's buffer, the bus's byte order.

Building it yourself

Advanced user

The source is on GitHub under the GPL v3. A build needs the ARM GNU Toolchain 14.2 and atarist-toolkit-docker for the ST's side:

./build.sh pico_w release 44444444-4444-4444-8444-444444444444

The firmware lands in dist/ as a UF2 and its descriptor. The last argument is the app's identity: use the development UUID above for your own builds; the store's is in desc/app.json. With a Raspberry Pi Debug Probe on the cartridge, tools/dev/flash.sh builds, flashes and checks a build in one go. Builds are reproducible: the release is dated by its commit, so a local build of a tagged commit with the same date gives the same bytes, and its MD5 is in the store's descriptor. make -C tests/host test runs the host tests in a few seconds.
